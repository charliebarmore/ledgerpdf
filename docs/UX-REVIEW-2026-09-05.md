# LedgerPDF v0.3.1: product review and next test plan

Reviewed September 5, 2026. Latest published release verified through GitHub:
[v0.3.1, August 17, 2026](https://github.com/charliebarmore/ledgerpdf/releases/tag/v0.3.1).
The reviewed HEAD was `ead0409`; the installed macOS app also reported 0.3.1.
Subsequent implementation and test results are recorded in
[ENGAGEMENT-ACCEPTANCE.md](ENGAGEMENT-ACCEPTANCE.md); this review preserves the
observations that motivated that work.

## Working diagnosis

The owner clarified the primary job: **compile the final master file for an
engagement from its documents and workpapers, with an agent assembling the binder
and performing the first pass before a human opens it for review.**

The product should therefore organize around preparation and handoff:
**engagement files → agent compilation and first pass → human review → final
master file.** Manual annotation supports that workflow. Agent compilation is
the main entry point, rather than an advanced feature to test later.

The initial recommendation to prioritize a manual workflow and make agent use
optional has been superseded by this clarification. The observed UI complexity
still matters, but the remedy is to make agent preparation and human review
coherent. “Ahead of its time” remains a hypothesis about adoption, not a finding
that the underlying job lacks demand.

The accepted organizing standard is the prior-year master, qualified by current-year
instructions. Compilation is one-shot into a fresh binder; updates after human
edits are deferred. See [DECISIONS.md](../DECISIONS.md) for the canonical decisions.

## Proposed compilation and handoff contract

1. **Give the agent the engagement.** Select the input files/folder, the ordering
   reference, and the destination. Initial setup identifies the connected agent
   and its access; ordinary runs should not require a terminal command or a long
   custom prompt. The current app exposes MCP tools to an external agent; an
   in-app compilation action would need orchestration that is not yet implemented.
2. **Compile a candidate master file.** Inventory the inputs, convert supported
   documents, group them into sections, preserve useful source bookmarks, and
   create consistent navigation. Record every included, excluded, failed, and
   uncertain item with its reason and source. Suspected duplicates and conflicting
   versions need an explicit disposition; do not silently choose by filename.
3. **Perform the first pass.** Provisionally scope this to organization,
   conversion/readability, expected-document coverage where an expectation is
   provided, and specified totals/ties with traceable source figures. Record
   agreement, discrepancy, and inability to check separately. A missing document
   can only be identified against an expectation, not inferred from an empty
   search. This scope is a proposal, not a claim that all checks already exist.
4. **Hand off a reviewable binder.** The first screen answers: what was assembled,
   what the agent checked, what it could not check, and what needs a human.
   Findings jump to their supporting pages. Inventory and exclusions survive
   save/reopen, including failures with no page in the binder. Distinguish
   “Compilation complete,” “First pass complete,” and “Human review complete.”
5. **Finish the engagement.** The human can correct organization and marks,
   resolve findings, and save the final master. Keep the editable master as the
   central artifact. Creating a permanent send-out copy remains a separate task;
   a final engagement master does not necessarily mean an external delivery PDF.

Agent compilation should produce a candidate without modifying source files.
Recompilation after human edits must preserve the reviewed master and make
changes inspectable; current run-level undo does not restore structural changes.
The candidate/recompilation behavior is a requirement to design, not an existing
snapshot capability.

## What already exists and what needs connecting

Source review of `app/src/mcp/server.ts` confirms these building blocks:

| Existing capability | Remaining product work to validate/design |
| --- | --- |
| `binder_add_folder` inventories and imports supported formats, naturally sorts paths, and returns skipped/failed reasons. | Apply engagement-specific organization; persist the input manifest and dispositions for the human. The scanner currently limits imports to 200 eligible files and recursion to four levels; dotfiles and non-file/non-directory entries are skipped without an itemized response. |
| Page moves, bookmarks, and `binder_inventory` expose the assembled structure. | Compare the assembly against the intended master-file order and all original inputs, including inputs that never became binder sources. |
| `binder_read_page`, `binder_read_cells`, `binder_find`, `binder_foot`, and `binder_tie` support reading and recorded checks. | Define which checks the engagement requires; validate extracted figures and their meaning. Exact arithmetic cannot establish that the agent selected the correct figures. |
| `binder_summary`, `binder_add_cover`, and `binder_review_queue` support a handoff. | Make this the human's landing experience, persist compilation exceptions, and distinguish unchecked work from passed checks. |
| Attribution, history, and agent-status confirmation support human supervision. | Make corrections and reruns understandable without assuming structural changes can be undone by reverting a run. |

These are verified tool capabilities, not evidence that an agent has completed
the proposed engagement workflow successfully. No such agent run was performed
during this review.

## Evidence and limits

- Read the release history, design guidance, renderer, save/review controls,
  thumbnail implementation, test scripts, and CI configuration.
- Used the installed macOS app with a copy of a synthetic three-page PDF:
  inspected the empty screen, opened the document, placed a tick, opened Review,
  and saved a separate working binder in `/private/tmp`.
- Independently read the saved synthetic binder with the engine: three pages,
  one tick, an intact embedded session, and matching page geometry. A manual
  close/reopen of this installed-app artifact was not completed.
- Typecheck passed. Model checks: **309/309**. Persistence, preferences, and
  registration checks: **17/17**. Recovery checks: **5/5**.
- The initial recovery attempt could not start the local Vite server because
  the sandbox refused its listener. The rerun with the required local execution
  permissions passed; the first attempt is not evidence of a product defect.
- Native UI automation intermittently timed out or failed to activate a control
  through its accessibility index. Coordinate interaction worked for several
  controls. These are automation limitations, not established user-facing bugs.
- This was not a full regression run, a fresh-user study, a Windows evaluation,
  a large-binder benchmark, or a new cross-viewer conformance run. The installed
  app already had reviewer preferences. No client documents were used.

## A concrete engagement acceptance test

Start with one synthetic engagement packet and a human-prepared reference
master file. Write an answer key covering expected sections, input dispositions,
page coverage, checks and planted exceptions. Include PDFs, a multi-sheet
workbook with wide columns, a memo, a scan, an exact duplicate, competing file
versions, one unreadable/unsupported item, and an intentional numerical mismatch.
Supply a checklist if the agent is expected to detect a missing document.

Give the agent the packet and the organizing/checking instructions, without
coaching it through individual tool calls. Have a reviewer who did not watch
compilation open the result. The test is whether that reviewer can finish the
engagement more easily than by assembling it themselves.

| Stage | Success criterion | What to measure |
| --- | --- | --- |
| Start | The user can select the engagement, organizing reference, and destination and initiate compilation. | Setup time, repeated instructions, requests for help. Separate first-time setup from repeat use. |
| Assembly | Every in-scope input has an accurate persistent disposition; required pages are legible, correctly ordered, and navigable. | Silent omissions, incorrect version choices, clipped sheets, broken bookmarks, organization corrections. |
| First pass | Specified checks have correct evidence; planted discrepancies are found; unavailable/ambiguous evidence is explicitly unchecked. | Missed issues, false alarms, wrong-figure comparisons, unsupported claims of completion. |
| Handoff | A human who did not see the agent conversation can identify omissions and unchecked work and navigate to each finding. | Time to understand readiness, time per finding, need to consult chat history. |
| Finish | Human corrections survive save/reopen; the editable master is intact and clearly identified. | Correction time, lost work, page/mark alignment, confidence (1–5). |
| Future update (deferred) | Recompilation after human edits is outside v1. | Preserve source and reviewed binders; any repeat compilation starts at a new destination. |

Proposed acceptance gates:

- Zero silent in-scope input omissions, wrong-page marks, overwritten originals,
  or unreported conversion failures in the reference packet.
- Every planted required-check discrepancy is surfaced and every intentionally
  uncheckable item is represented accurately. Record false positives as well.
- Every finding and claimed passed check is traceable to evidence. No unchecked
  or agent-checked work is represented as human reviewed.
- Persistent inventory and exceptions remain usable after save/reopen without
  access to the agent conversation.
- Measure total **human setup + review + correction time** against manual master
  compilation; report agent elapsed time separately. Set the improvement target
  after measuring the baseline, rather than promising a percentage now.

Repeat agent runs on the fixed packet to expose variability; record model,
instructions, tools, and run outputs. Once the workflow passes this acceptance
test, recruit five preparers/reviewers for directional usability sessions on
equivalent packets, alternating baseline/prototype order where practical. Aim
for at least 4/5 completing setup and handoff without facilitator help. Validate
across additional engagement shapes before interpreting this as general quality.

## Engineering coverage to add next

Keep the existing model, persistence, recovery, MCP, and viewer checks. Add
tests where they cross real user boundaries, rather than duplicating model
assertions with more UI assertions.

1. **One complete agent-to-human handoff.** Fresh preferences → select engagement
   and organizing reference → agent compilation → recorded first pass → open
   review handoff → human correction → save → close → reopen. Check the resulting
   PDF/session and persistent input dispositions independently.
   Current smoke scripts include real renderer interactions, but also use
   `WPT_DEV_*` import/export/placement hooks; these do not prove native file
   dialog discoverability or a novice's ability to choose the right command.
2. **Review meaning.** A tick alone does not complete page review. An unresolved
   discrepancy remains discoverable. New findings after review reopen attention.
   Agent-proposed reviewed status still needs human confirmation. Verify the
   visible language as well as model state.
3. **Interruptions and recovery.** Preserve existing recovery/cancel coverage;
   explicitly walk an unsaved page reorder plus marks through recovery and check
   that the user receives an honest explanation of what can be recovered.
   v0.3.1 protects structural recovery evidence but does not promise automatic
   restoration of every unsaved structural change.
4. **Realistic scale.** Run 30/100/300-page mixed packets on Apple silicon and a
   representative Windows 1080p laptop. Measure startup-to-usable-page, page
   navigation, drag responsiveness, memory, save time, and visible feedback.
   Keep hardware and packets fixed; set performance budgets from the baseline
   and user tolerance rather than inventing passing numbers.
5. **Keyboard and display.** Verify all core tasks without a mouse, modal focus,
   and legibility at 1100×700 and 1440px width, including Windows display scaling.
   The current toolbar-fit contract is useful but does not measure comprehension.
6. **Export trust.** Include rotated/cropped pages, scanned and text PDFs, forms,
   existing annotations, long bookmarks, and mixed imports. Reorder, save twice,
   reopen, and inspect both editable and send-out files. Run existing pdfium /
   poppler checks and the manual Acrobat checklist for relevant changes.

## Scope for the next iteration

Prototype the compilation entry point and the human review landing experience
using the existing design language. Keep common correction tools available in
context, preserve familiar shortcuts, and retain the single editable PDF model.
Use the reference engagement acceptance test to determine what must be built
between the existing tools, before undertaking a broad toolbar redesign.

The first-pass scope above is deliberately a concrete starting proposal. The
owner's organizing standard and engagement-specific checking instructions should
refine it. The central product measure is whether a person receives a complete,
understandable master file that takes less effort to review and finish.
